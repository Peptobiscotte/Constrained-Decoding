# Call Me Maybe

## Description

Call Me Maybe is a Python activity focused on **LLM function calling through constrained decoding**.

The goal is to take a natural-language user request, select the most appropriate function from a predefined set of function definitions, extract the required arguments, and produce a valid structured JSON result.

Instead of accepting unrestricted model output and repairing it afterwards, the project constrains token generation while decoding. At every generation step, invalid token candidates are masked so that the model can only continue with outputs compatible with the expected function name, JSON structure, and parameter type.

The implementation uses the provided `llm_sdk` and a small language model. Function definitions and prompts are loaded from JSON input files and validated with Pydantic.

## Algorithm explanation

The constrained decoder is divided into two main phases.

### 1. Function selection

Each available function name is tokenized before generation. The language model receives the user request together with the available function names and their descriptions.

During decoding, the current generated token sequence is compared with the tokenized function names. Any token that would make the generated sequence cease to be a prefix of every available function name is assigned a logit of negative infinity. The model therefore remains responsible for choosing the function, while the decoder guarantees that the final result is one of the declared functions.

Generation stops when the produced token sequence exactly matches a complete function name.

### 2. Parameter generation

Once the function has been selected, its parameter definition is retrieved programmatically. From this definition, the program builds a sequence of decoding steps.

A step is either:

- **fixed**: JSON syntax or other content that must be reproduced exactly;
- **variable**: a value that must be generated by the model according to its declared type.

The decoder then walks through these steps sequentially. Fixed sections only allow tokens matching the expected token sequence. Variable sections apply type-specific constraints.

#### Boolean values

Boolean generation is restricted to the token sequences representing valid JSON boolean values. Candidates that are not prefixes of an allowed boolean value are masked.

#### Number values

Numbers are validated incrementally. The decoder distinguishes between a valid number prefix and a complete number. This allows values such as `-`, `2`, `2.`, and `2.5` to be handled correctly during generation without prematurely stopping at the first valid digit.

When a number is complete, the fixed token belonging to the next JSON step can be selected, allowing the decoder to leave the number state.

#### String values

Strings are required to start with a JSON quote. The opening quote is constrained explicitly before the model generates the content of the string. Prefix validation ensures that the generated value remains compatible with a JSON string, and completion is detected only after a closing quote has been produced.

Regex parameters are handled as string values while additional constraints can be applied during their generation to prevent undesirable repetitive constructions.

### 3. JSON validation and output

The complete generated response follows this structure:

```json
{
  "prompt": "...",
  "name": "fn_name",
  "parameters": {
    "parameter": "value"
  }
}
```

Prompt text is serialized correctly when inserted into the generated JSON so that quotes and other JSON-sensitive characters are escaped without modifying the original logical prompt value.

The final response is parsed with Python's `json` module. A parsing failure therefore reveals an error in the constrained generation rather than being silently repaired afterwards. Valid results are appended to the JSON output file.

## Design decisions

The implementation separates function-name selection from parameter generation. This keeps each decoding phase focused on a single responsibility and makes the constraints easier to reason about and test.

A step-based representation was chosen for parameter generation instead of building one monolithic token template. It provides an explicit distinction between deterministic JSON syntax and values that must remain under control of the language model.

Type constraints operate on prefixes rather than only complete values. This is important because autoregressive generation must determine whether each intermediate candidate can still lead to a valid final value.

The final JSON is generated through constrained decoding rather than generating arbitrary text and correcting it afterwards. Programmatic validation is used as a final correctness check.

## Performance analysis

Constrained decoding improves structural reliability because impossible outputs are removed before token selection. Function names, booleans, numbers, and fixed JSON sections can therefore be generated deterministically with respect to their grammar.

The main performance cost comes from evaluating candidate tokens and applying validation rules at every decoding step. The small model must also perform another forward pass after every selected token. As constraints become more complex, particularly for free-form strings and regular expressions, generation can become slower.

Reliability is highest for domains with small and explicit grammars, such as function names and booleans. Free-form strings and regex values remain more dependent on the semantic quality and repetition behaviour of the language model because many syntactically valid continuations may exist.

## Challenges faced

### Token-level prefix matching

A function name is not necessarily represented by a single token. Function selection therefore had to operate on token-sequence prefixes rather than decoded strings or individual vocabulary entries.

### Distinguishing prefixes from complete values

Numbers exposed an important difference between a valid prefix and a finished value. For example, `2` can already be a valid number but may also be the beginning of `2.5` or `233`. Separate prefix and completion checks were introduced so that generation does not terminate prematurely.

### String termination

A single opening quote is a valid prefix but not a complete string. String generation therefore tracks its initial state explicitly and distinguishes the opening quote, string content, and final closing quote.

### Regular-expression generation

Regex parameters provide a particularly large valid search space. Small language models may repeatedly extend an already valid expression with constructs such as escaped character classes or quantifiers instead of selecting the closing quote. This highlighted the difference between syntactic validity and semantic usefulness and motivated dedicated regex constraints and termination safeguards.

### JSON escaping

Input prompts can themselves contain quotes. Directly inserting such text into the output template produces invalid JSON. JSON serialization is therefore used for fixed prompt values so that the original prompt remains unchanged while its textual JSON representation is correctly escaped.

## Testing strategy

The decoder was tested incrementally rather than only through complete end-to-end examples.

Function selection was first tested independently to ensure that only declared function names could be generated. Parameter generation was then tested separately for booleans, integers, floating-point values, negative values, strings, and regex strings.

Intermediate candidate tokens, logits, current steps, and decoded responses were inspected during development to identify cases where a valid candidate was incorrectly masked or where the model failed to leave a variable-generation state.

Finally, generated responses are passed through `json.loads`. This provides a strict end-to-end check that the constrained output is syntactically valid JSON before it is stored.

Static validation is performed with:

```bash
make lint
```

## Example usage

Given a request such as:

```text
What is the sum of 2.5 and 3?
```

the program can select the appropriate function and produce a structured result such as:

```json
{
  "prompt": "What is the sum of 2.5 and 3?",
  "name": "fn_add_numbers",
  "parameters": {
    "a": 2.5,
    "b": 3
  }
}
```

Another example:

```text
Greet john
```

can produce:

```json
{
  "prompt": "Greet john",
  "name": "fn_greet",
  "parameters": {
    "name": "john"
  }
}
```
